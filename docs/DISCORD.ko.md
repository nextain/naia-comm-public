# Discord 기반 협업 설계

프로젝트마다 Discord 앱은 하나만 둡니다. 게이트웨이 실행체는 이 저장소에 포함되지 않으며 프로젝트 팀 개발 서버에서 별도로 운영됩니다. 게이트웨이는 팀 개발 서버에서 한 프로세스만 봇 토큰을 소유합니다. 여러 작업공간이 같은 토큰으로 Discord 연결을 직접 열지 않습니다.

공용 채널에서는 GitHub 이슈마다 스레드 하나를 사용합니다. 봇은 이슈 번호로 스레드와 작업을 연결하며, 멘션된 경우에만 응답합니다. 참여자는 이슈 양식에서 GitHub handle과 같은 소문자 별칭을 스스로 선언하고, 메시지 작성자는 `[별칭/프로젝트]`로 표시합니다. 운영진은 별칭과 실제 Discord ID의 연결을 런타임 등록부에 기록합니다. 이 등록부는 Git에서 무시되는 파일이며 공개 후보에 포함하지 않습니다.

개인 DM은 발신자의 등록 정보를 이용해 개인 SSH 작업공간을 선택할 수 있습니다. 하지만 DM은 병합·배포·DB 권한을 주지 않습니다. 등록된 작업공간에서 Codex 또는 Claude가 코딩을 지원할 수 있고, 결과는 GitHub 이슈에 남깁니다. 실제 공급자·모델 가용성은 실행 시점의 게이트웨이와 계정·환경 설정에 따릅니다.

원본 저장소의 스토어 검토 자료나 화면 예시에 OpenCode 표기가 있을 수 있지만, 그 자료는 이 공개 후보에 포함되지 않으며 현재 연결이나 공급자 가용성을 보장하지 않습니다. Grok은 이 트리에 별도 실행 진입점이 없고 로컬 보조와 읽기 전용 canary 검토 범위로만 기록합니다. 어느 도구도 Discord DM만으로 병합·배포 권한을 얻지 않습니다.

참여자 등록부는 `schemas/participants.schema.json` 형식을 따르며 `.runtime/participants.json`에 둡니다. 저장소에는 형식만 두고 실제 Discord ID, 사용자 계정, 작업공간 경로는 커밋하지 않습니다. 별칭은 프로젝트 안에서 중복될 수 없고, 한 발신자는 한 기본 작업공간으로만 연결합니다. 연결이 없거나 중복되면 봇은 추측하지 않고 등록 요청을 반환합니다.

게이트웨이의 책임은 다음뿐입니다.

- Discord 메시지 수신과 발신자 식별
- 이슈 및 스레드 연결
- 등록된 작업공간으로 작업 요청 전달
- 작업 ID와 결과 요약 반환
- GitHub 이슈에 기록할 근거 링크 제공

게이트웨이가 직접 운영 권한을 가지면 안 됩니다. 배포 명령은 프로젝트별 역할 정책과 이슈 승인을 별도로 검사해야 합니다. 동일 토큰의 두 번째 소비자가 발견되면 먼저 실행 중인 인스턴스를 추측해 종료하지 말고, 새 인스턴스가 실패 종료해야 합니다.
